Implement Phase 2 — Retrieval & RAG Engine v1.1:

Corpus Expansion, Retrieval Evaluation and Quality Hardening

Objective

Complete and validate the first production-ready version of the RRAI Retrieval & RAG Engine.

Retrieval & RAG Engine v1 has successfully established:

* Deterministic Markdown chunking
* A persistent derived knowledge index
* PostgreSQL full-text search
* Hybrid metadata ranking
* Context budgeting
* Lens-first filtering
* Retrieval provenance
* Admin diagnostics

However, the current runtime index contains only:

* 5 chunks from knowledge/Risk Rising.md
* 5 chunks from knowledge/LogicGate.md

This proves the retrieval mechanics, but not the usefulness or completeness of the RRAI knowledge corpus.

This task must:

1. Classify and index the wider governed knowledge repository.
2. Validate retrieval quality with a repeatable evaluation suite.
3. Prevent weak or irrelevant fallback results from entering prompts.
4. Establish measurable acceptance criteria for retrieval quality.
5. Confirm that lens and one-way-valve controls remain intact as the corpus expands.

Do not begin the Learning Engine until this task is complete.

5. Remove unsafe empty-query fallback behaviour

Review the current behaviour:

“Fallback to evidence-tier ranking when FTS finds nothing.”

This fallback may return authoritative but irrelevant content merely because no lexical match exists.

Change the retrieval policy so that:

* No-match queries do not automatically receive unrelated governed chunks.
* Evidence authority may adjust the ranking of relevant candidates, but must not create relevance.
* Results below a configurable minimum relevance threshold are excluded.
* The assistant may receive no static knowledge results when nothing relevant is found.
* A no-result condition is recorded in the retrieval trace.
* The prompt instructs the assistant not to imply that missing evidence was found.

A safe deterministic fallback may use:

* Exact acronym expansion
* Controlled synonym matching
* Tag matching
* Heading matching
* Query token normalisation

Do not fall back to arbitrary high-authority chunks.

Persist the policy version in every retrieval trace.

8. Result diversity

Prevent one large or repetitive asset from dominating the context.

Implement:

* Maximum chunks per asset
* Near-duplicate suppression
* Heading-path diversity
* Asset diversity where multiple strong sources exist
* A penalty for repeated substantially similar content

Do not force diversity when one source is clearly the only relevant authority.

Relevance and authority remain primary.

⸻

9. Evidence conflict handling

Create deterministic conflict metadata where retrieved sources materially disagree.

The retrieval engine does not need to resolve the dispute.

It must:

* Preserve the competing fragments.
* Identify their asset IDs and evidence tiers.
* Mark the result set as containing potential conflict.
* Pass a concise conflict instruction to prompt assembly.
* Instruct the assistant to distinguish authoritative fact, current operational understanding and unverified claims.

Do not use an LLM to decide source truth during retrieval.

11. Evaluation runner

Create a deterministic command such as:

pnpm --filter @workspace/api-server run evaluate:retrieval

The evaluation must report:

* Total cases
* Top-1 accuracy
* Recall@3
* Recall@5
* Mean reciprocal rank
* Empty-result rate
* Irrelevant-result rate
* Prohibited-asset violations
* Prohibited-partition violations
* Restricted-source violations
* Average selected chunks
* Average context size
* Average search latency
* P95 search latency

The runner must exit non-zero when a hard security boundary is violated.

It should also exit non-zero when agreed minimum quality thresholds are not met.

Set initial acceptance criteria explicitly.

Recommended initial gates:

* Prohibited-partition violations: 0
* Restricted-source violations: 0
* Cross-organisation violations: 0
* Recall@5: at least 85%
* Top-1 accuracy: at least 70%
* Irrelevant-result rate: below 10%
* P95 local search latency: below an agreed practical threshold

Adjust quality thresholds only when justified by the actual evaluation corpus.

Do not lower security thresholds.

14. Assistant behaviour when no evidence is retrieved

Update prompt assembly so the assistant can distinguish:

* Relevant governed evidence retrieved
* Permitted runtime memory retrieved
* No relevant governed evidence found
* Relevant evidence excluded by policy
* Evidence conflict present

The assistant must not imply that it found supporting knowledge when retrieval returned none.

It may:

* Answer from general reasoning where permitted.
* Clearly label assumptions.
* Say that the governed repository did not contain relevant evidence.
* Ask for source material where necessary.

Do not reveal hidden or prohibited source details.
